# 仓库结构速览

## 使用的工具

`list_files` 看骨架，`read_file` 读关键文件，`git_log` 看活跃度。
`search_code` 只在需要确认某个技术栈是否真的在用时才用，不要拿它做地毯式扫描。

## 步骤

1. 调用 `list_files`，不带 `glob`，先拿到完整文件清单。
   从路径的公共前缀判断出顶层模块划分，这一步不要读任何文件内容。
2. 挑出**最多 3 个**最能说明问题的文件读，通常是：
   - 依赖清单（`go.mod` / `package.json` / `requirements.txt`）——确定技术栈；
   - `README.md`——如果有，它往往直接回答了「这是干什么的」；
   - 目录里行数最多或名字最像入口的那个源文件。

   用 `read_file` 时带上 `end_line` 限制在 60 行以内，只看头部就够判断了。
3. 调用 `git_log`，`limit` 设 10，看最近的提交节奏和参与者。

## 输出格式

用中文输出：

- **这个工程是做什么的**：一到两句话。
- **技术栈**：语言、框架、关键依赖，各一行。
- **目录结构**：只列顶层模块，每个后面跟一句职责说明。不要贴完整文件树。
- **活跃度**：最近提交时间、主要贡献者、大致节奏。

## 注意事项

- 全程控制在 5 次工具调用以内。这个技能的价值是「快」，读得越多反而越偏离目的。
- 不要因为文件多就逐个去读，从路径命名推断职责是可以接受的，
  但推断出来的结论要用「看起来是」这类措辞标注，和读过的事实区分开。
- 如果 `list_files` 的返回被截断了，说明仓库很大，直接基于已有部分做判断并说明这一点。
